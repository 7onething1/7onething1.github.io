The four verdicts

The diagnosis is right about the cost per turn and right about the engine being unfinished. Four of its specific, actionable claims do not survive the local check, and the largest single context item in the system is one it never counted.

Held

Per-turn context cost is real. Measured 625,521 cache-read tokens per assistant turn on September 10, against the audit's figure of roughly 556,000 for the Shiner session.

Confirmed by independent measurement of the transcript's own usage records. This is the claim that carries the remediation.

Wrong target

The three scripts the audit says to edit do not exist. run_gates.py, completion_stop_hook.py and no_stop_gate_hook.py return nothing from a find over all of ~/.claude.

The real Stop chain is 16 hooks under different names. Following the instruction verbatim would edit nothing and report success.

Worse than stated

The engine has zero bytes of executable Python. The audit describes a CLI that could import and inspect files with three commands missing. There is no CLI.

Eight empty __init__.py files, ten empty directories, and a SKILL.md that already marks the package not implemented.

Unverified

The headline totals are not reproducible on this Mac. Twelve concurrent sessions, 1,610 assistant turns, 496,941,520 cache-read tokens. September 10 here holds 1 session, 70 turns, 43,786,490 tokens.

Brandon runs two Macs. A MacBookPro scan is the one diagnostic this machine cannot run, so these four figures stay labelled unverified rather than refuted.

My first census was wrong, and it understated the problem

An earlier pass of this page said 11 of 14. That came from grepping for a "decision" block field and a literal exit(2), which misses the return 2 plus sys.exit(main()) form. Three gates block that way and were miscounted as silent: completion_stop_gate.py, chat_link_gate.py and chat_donelink_gate.py.

Direct proof rather than inference: five of these gates blocked this very session, including two of the three I had called non-blocking. A grep for the word block is the wrong instrument for a census of blocking.

The 17th hook was the audit's own thesis, running until this afternoon

That prompt-judge is worth reading, because it is the recursive stop the audit describes, built on purpose. It instructs: if Claude "says it is stopping, pausing, queuing work, leaving an item for later, asking whether it should continue" then return INCOMPLETE and direct Claude to perform the remaining work. Its reason text is fed back as Claude's next instruction.

Two costs follow. A type: "prompt" hook spends a full model call on every stop, which no script in the chain does. And a judge told to refuse any stop that mentions queuing will refuse stops it cannot clear. The session log for this machine records it looping about 12 turns on a blocked external dependency before it was switched off, which is that session's report rather than a measurement of mine.

The audit asked for recursive stopping to be removed from two scripts that do not exist. The real instance was a prompt-judge, and Brandon had already removed it hours before this page was first written.

The chain does not short-circuit, so the cost compounds

Whether a block at one gate stops the rest from running decides how expensive an unmet stop is. This session answered it by accident. On one Stop event, gates at positions 5, 6, 8 and 13 all blocked and all reported, so the chain ran past the block at position 5 and kept going to position 13.

That means a single unmet stop can collect refusals from up to fourteen gates at once, and each refusal costs a fresh turn carrying the whole conversation. Bounding only the first blocker would do nothing. Every gate needs its own counter, which is what makes the block-block-pass test the first item of Phase 1 rather than a detail inside it.

These counts are a snapshot, and one moved during the review

Hook counts change while sessions run. The first read at 13:0x returned 17 Stop entries. A re-read at 13:41 returned 16, because settings.json was written at 13:28:06 by one of the two other sessions live on this machine, which left a backup named settings.json.bak-before-guitar-evaluator-off-2026-10-17.

Diffing that backup shows what was removed: the 17th Stop hook was an LLM prompt-judge, a {"type": "prompt"} entry rather than a script, and it was turned off at Brandon's request. Its verbatim copy sits at hooks/DISABLED-guitar-completion-evaluator-2026-10-17.json. So Stop held 17 executable hooks before the edit and 16 after. The 14-gate blocking census below is unaffected, and all 14 Python gates are genuinely wired to Stop.

An earlier pass of this page called that entry a blank placeholder, which was wrong. The extraction read each hook's command key, and a prompt-judge hook has none, so a live model-call hook was recorded as an empty string.

One gate is already solved, and it is the pattern to copy

An earlier pass of this page called completion_stop_gate.py a silent blocker and read the comment at its line 301 as a live defect. Both readings were wrong. It blocks with return 2 through sys.exit(main()), and line 302 writes the refusal reason to stderr before it does.

That line-301 comment documents a bug that was already fixed on 2026-09-14, when 45 refusals reached Claude with no reason because the text went to stdout. A regression test ships with the fix and passes today, measuring exit 2 with 596 characters of stderr.

It is also already bounded, at HARD_CAP = 25 with a COMPLETION_GATE_CAP override, and its counter is keyed per session. It even carries the fix for the trap the other thirteen will hit: on 2026-09-14 every counter read 1, because the refusal feedback was itself being counted as a fresh user record and resetting the count. So the real target is the 13 gates with no bound, and the work is to copy this one rather than invent a mechanism.

The three-phase plan

Ordered so that the cheapest fix with the widest effect comes first, and so that no phase's evidence depends on a phase that has not closed.

Phase 1

Bound the supervisor and shrink the baseline

Add a per-session block counter to each of the 13 unbounded Stop gates, copying the HARD_CAP shape completion_stop_gate.py already uses, with a ceiling of two consecutive blocks on the same reason and a third attempt that passes through stating the hook and the unmet condition. Avoid the trap that gate documents, where every counter read 1 because the refusal feedback was itself counted as a fresh user record. Then move the long trigger lists out of each front-matter description into the skill body, following the POINTERS.md pattern.

The Stop chain goes first because every later phase ends in a stop, so an unbounded block loop on a phase-2 stop costs a multiple of what it costs today. Edit the hook scripts rather than settings.json, which is a contested file and where the audit records a permissions deadlock.

Exit: each of the 13 unbounded gates passes a block-block-pass test; measured auto-loaded baseline under 25,000 tokens, down from 49,989; cache-read per turn re-measured against today's 625,521.
Phase 2

Build the engine against the schema, tests first

A greenfield build with the data contract already settled by the 16,916-byte IR schema. Minimum surface: doctor, import, map, generate, write-midi, verify. doctor exits 0 only when the other five run on the bundled fixture.

The note-level tests are written before the generator that must pass them, because the audit records two gates that passed on the wrong question: a scorer that rewarded unchanged harmony with 102, and a melody collision check that compared against chord roots and so let compound minor ninths through. Each test is run against its recorded bad input first and must fail there before it is trusted on good input.

Exit: bin/reharm doctor exits 0, and every note-level test fails on its recorded bad case then passes on the fix. Watch: a fixed-shape exporter writes a full-size empty MIDI and exits 0, so verify reopens the file and counts notes against the input.
Phase 3

One song, then the outstanding scan

One Shiner song end to end: mapped, three harmonically distinct candidates, melody and bass preserved, MIDI exported, reopened, and passing the phase-2 tests with named bars and pitches. One song per pass. Then the MacBookPro transcript scan, which closes the only diagnostic this machine cannot run.

The showcase is rebuilt from the phase-1 and phase-3 measurements side by side: baseline before and after, cache-read per turn before and after, block counts before and after, and the per-candidate test results.

Exit: three candidates on disk, tests passing, page live at http 200, fraud check green. Goal metric: model turns per verified playable arrangement, undefined today because the count of verified playable arrangements is zero.
