1. The short answer

The MacBook did not find a faster setting. It wrote its wasted time down as ten named mistakes, each with an executable fix. Its own first finding was that switching off 52 unused skills buys nothing: they load as bare names, roughly 1,300 characters of an 88,000-token start. The waiting is the model thinking. So the gain came from the list of mistakes, not from configuration, and the same method applied here turns up one failure far larger than anything on the MacBook's list.

4. Where this Mac's written gate failed

Batching has been a hard gate in CLAUDE.md since the 2026-07-19 session audit, and it has a memory file of its own. Both are prose. Here is what prose produced:

CLAUDE.md, since 2026-07-19 : "independent tool calls go out in ONE block, target above 40%"
measured 2026-10-19         : 540 of 9,009 turns batched = 6%
one session the same day    : 64 tool turns, 0 batched = 0.0%
The lesson generalizes past batching. Of the 52 hooks on this Mac, none measured tool-call shape. Every other hard gate that holds here holds because something runs and refuses: the deploy gate, the delete block, the voice gate, the stop gate. The rules that live only in a document are the ones that drift, and the measurement is how you tell which is which.

5. The four checks that shipped

The first three read a signal the audit measured. The fourth reads one the audit does not measure at all, found by parsing this session's own transcript. Each prints a single line, and returns zero on every path, so none of them can block a tool call. Each was run against inputs with known answers in both directions before being wired.

batch_streak_gate.py, PostToolUse on Bash, Read, Grep and Glob

Counts tool calls per assistant turn and speaks when four turns in a row have each carried one call, then stays quiet until the next multiple of four. A batched turn clears the run.

3 singles        -> quiet     (expected quiet)
4 singles        -> FIRED     (expected fire)
5 singles        -> quiet     (expected quiet, between thresholds)
8 singles        -> FIRED     (expected fire)
4 then batched   -> quiet     (expected quiet)
5 of 5 correct, plus malformed stdin / empty payload / missing file all exit 0

write_tool_nudge.py, PreToolUse on Bash

Flags a command that writes a file through a shell redirect: echo, printf, a cat heredoc, or tee. Silent for /dev/null and for throwaway fixtures under the scratchpad, where a redirect is the right tool.

  tee into a report            python3 run.py | tee _outputs/r.txt
  printf into a file           printf "a\n" > ~/a.txt

duplicate_read_gate.py, PostToolUse on Read

Counts reads per real path per session and speaks on the third read, then every third after it. Different spellings of one file collapse to a single count, and a read that asked for a line range is told so rather than scolded.

invocation_failure_gate.py, PostToolUse on Bash

Speaks when a command failed because its invocation was guessed: a wrong flag position, a wrong subcommand, a binary this Mac does not have, a path belonging to the other Mac, a zsh glob that matched nothing, or a validator refusing the record shape it was handed. Each message carries the specific remedy rather than a scold.

KNOWN FALSE POSITIVE, disclosed: reading a log that QUOTES a failure
fires it. The cost is one extra line, since it nudges and never blocks.
Why negative controls and not just positives. On 2026-08-29 a cymbal-detection fix on this Mac passed its one positive control, shipped, and then failed a negative control that was already on disk at the time. Each of these three carries both halves, so a check that simply fires on everything would have shown up as a wrong answer rather than as a success.

The fourth row is the one the audit could not see. session-audit reports batching, redirects, duplicate reads, skill and agent counts, and cache health. It has no measure for a call that failed because its flags were guessed, so nothing counted those until this session's transcript was parsed directly: 12 of 126 tool results, 9.5%, five of them a validator rejecting a record shape and three a wrong flag or subcommand. A scorecard only governs what it thinks to count, which is the same lesson one layer up from the prose gates.

Three limits remain, none of them hidden. Every check is a nudge rather than a refusal, chosen so that a block never breaks a legitimate pipeline. The fourth fires on a log that merely quotes a failure. And whether the session that wired them loaded them is now settled: it did not, proven by probe at 14:46, because the settings watcher only watches directories that held a settings file when the session began. A new session loads all four.
