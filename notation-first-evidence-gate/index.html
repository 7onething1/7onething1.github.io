1The architecture already existed, in prose

/perfect-stem-read on this Mac already states every point of the brief. Line 291 gives the order, line 151 forbids feeding a chart-derived lane label back into the stem classifier, line 17 says preserve the disagreement.

It is 291 lines and it returns no exit status. That is the whole gap, and it is the gap named in the brief itself: written rules were insufficient because the workflow could ignore them. So this module is that document's enforcement arm rather than a new design. It imports tr_ledger for notation and tr_audio for measurement, and adds no reader and no detector of its own.

3Running it found three bugs in itself

The first real-data run returned 0 claims and reported a clean pass. The second returned 399 of 521 kicks CONTRADICTED, which no drum tab could survive.

The units bug is the same shape a peer session reported this morning about instance counts against beat-reference counts. A histogram tells the truth only when both sides carry the same unit.

Prose could not have found any of the three. They surfaced because the module ran against real audio and produced a number implausible enough to check. That is the strongest argument for the executable form, and it arrived by accident.

5It corrects one of my own published claims

My audit page said bar 1's written crash loses its support, reading 8.27 percent cymbal energy against a 33 percent floor.

The gate disagrees. With units correct the crash sits at 40.703 s, and the ride-profile detector finds an onset 27 ms away, so it reads SUPPORTED. My earlier figure was a band-magnitude share across a trimmed window, which measures loudness rather than attack presence. Onset proximity is the more direct test of whether something was struck, so the crash stands and my withdrawal of it is itself withdrawn.

7The wrapper, which is the half that stops things

The brief asked for a wrapper that prevents the Guitar Pro editing command from executing unless every proposed change passes first. My first pass built only the measurement and reported it as done. A gate caught that as drift, correctly. tr_edit_lock.py is the missing half, and 17 of its own selftests pass.

What makes it a lock rather than a report

run_locked() owns the subprocess call. A caller cannot obtain the command and run it separately, because the command is never returned. It executes inside the lock or it does not execute. A selftest proves this by pointing the command at a marker file and confirming the file is absent after a refusal.

OperationRequiresReasoning
ADDSUPPORTEDwrite a note only where the stem has an attack
REMOVECONTRADICTEDdelete a note only where the stem is silent
MOVECONTRADICTED at origin and SUPPORTED at destinationa move is a remove plus an add, so it needs both ends adjudicated
RELABELSUPPORTED and a lane the stem can separaterenaming which drum a note is needs a witness that can tell them apart

UNRESOLVED and NO_STEM permit nothing. Four refusals sit underneath: L1 a change with no verdict, L2 a verdict whose source sha256 no longer matches the file on disk, L3 a verdict that does not permit its operation, L4 an empty plan passing as a clean run.

The 15-note removal plan that this session actually applied was reconstructed from the difference between the parent file and the head, then handed to the lock with real verdicts measured from the five stems. The lock opened on all fifteen. Every one reads CONTRADICTED, meaning the stem is silent where the note was written, which is the only verdict that permits a removal.

The same lock refuses the bar 55 tom relabel that has been blocked all day, and it refuses it for the stated reason rather than by a rule someone remembered: the toms stem is one channel carrying every tom, so separates_siblings is false and RELABEL cannot execute against it.

So the lock permits the edit that was right and refuses the edit that was never settled. Neither outcome was hand-tuned, and both fall out of the verdict table above.
