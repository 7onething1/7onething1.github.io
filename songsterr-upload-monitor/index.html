Which revision is new, and what is in it

This was the actual complaint. Songsterr shows a revision id and a timestamp and nothing else, so when a session uploads, and Brandon uploads, and a third session uploads over both, nothing on the page records who made which one. Two sessions today held opposite beliefs about who made r8516072.

The vocal track a name check misses

"Make sure each is doing it with a file with vocal drum etc" has a trap on this exact tab. The fifth part carries the vocal line. Measured on s5823892:

  • the track has no name at all, an empty string
  • the instrument is Tenor Sax, General MIDI program 66
  • the lyrics array is empty, zero entries
  • it holds 310 notes across 69 bars

The pipeline writes vocals onto a Tenor Sax patch, and the upload gate knows to classify by name rather than by program for that reason. On a tab that has been round-tripped through Songsterr the name is gone entirely, so the classifier returns other:tenor sax:

# measured, not asserted
part4 name      : ''
part4 instrument: Tenor Sax / id 66
newLyrics       : list, len 0
notes           : 310 across 69 bars

role_of('Tenor Sax')             -> 'other:tenor sax'
role_of('Tenor Sax', program=66) -> 'other:tenor sax'

VERDICT: a name-based full-band check reports NO VOCAL
         on a tab that has 310 notes of vocal line.

A gate reading that as a missing vocal would either block a good upload or wave through a file that really did drop the part. Full band gets verified by per-part note content, and not from what the track is called. That is now written into the skill.

The lock

importRevisionInput replaces the entire tab. Two overlapping imports do not merge. The second one wins outright and the first session's work is gone with no error raised anywhere, which is how a five-track tab became a one-track tab on a previous occasion.

The deploy pipeline already solved this shape for Vercel: one door, a flock, concurrent ships wait their turn. A flock is no use here, because an upload spans many tool calls across many turns and a flock dies with the process holding it. So the new tool takes a lease: a file that records the holder, with an expiry, taken before the browser is touched and released once the upload finishes.

# before touching the browser
upload_lease.py acquire --session "Theship tabs delivery handoff" \
    --song "02 Flake" --tab s5823892

# after the upload finishes
upload_lease.py record  --session "Theship tabs delivery handoff" \
    --song "02 Flake" --tab s5823892 --rev r8516072 \
    --tracks 5 --roles vocal,drums,bass,guitar,guitar
upload_lease.py release --session "Theship tabs delivery handoff"

upload_lease.py status              # who holds it right now
upload_lease.py latest --tab s5823892   # which revision is new, and whose

The lease self-expires after twenty minutes, so a session that dies mid-upload cannot deadlock the others. That is deliberate. A stuck lock is worse than a race, because a race at least gets noticed.

What changed, so this does not need watching again

  • Every session was messaged with the rule, the lease commands, and the specific finding it needed. The two parked ones got the note diff so they rebase rather than overwrite.
  • The rule now lives in the skill itself. songsterr-upload/SKILL.md now opens with it, so a session that never sees this page still gets it.
  • The ledger answers the original question. Every upload appends the song, the tab, the revision, the track roles it carried, and who did it. Brandon's hand-uploads are recorded too, marked --source brandon. Both Flake revisions are already seeded from the live backup.
  • A recorded upload missing vocal, drums, bass or guitar gets flagged in the ledger at write time, so a thin file leaves a trace rather than passing quietly.
