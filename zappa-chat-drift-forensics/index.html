Why the drift happened

The amendment written later that same week added a third branch for exactly this state. It says the chat does not end, and it keeps working evidence on the same song. What finishing the work then found

Brandon's call, "i already said brown wins", settled the opening barring. Ryan Brown's DRUM Magazine chart covers bars 1 to 9, so Brown decides the 10/16 split into 5/16 plus 5/16 and casts no vote past bar 9. Applying that and then verifying the built file against the author's own surfaced a defect nobody had counted.

The author writes a five-step descending tom run. The built file had four steps with the bottom drum doubled. The earlier note called it "one slot" in each of two bars. It was ten note slots, five per bar, and the run had lost a step.
FileBars 4 and 15 (author numbering)
author r7115188 Snare 5, High Tom 5, Mid Tom 5, Low Tom 5, Very Low Tom 5
rev5 Snare 5, High Tom 5, Mid Tom 5, Very Low Tom 10
rev6b Snare 5, High Tom 5, Mid Tom 5, Low Tom 5, Very Low Tom 5

Read the kit's own names, never General MIDI

This file's drumKit table defines idx 12 as Low Tom (hit) at OutMidi 45 and idx 13 as Very Low Tom (hit) at OutMidi 43. General MIDI calls 43 "High Floor Tom", which is wrong for this kit and would have mislabelled the whole diagnosis. The articulation tables in the author file and the built file are identical, so the comparison holds.

The repair, measured

master bars 115 -> 115 total note count 7481 -> 7481 drum track notes 1576 -> 1576 ghost notes 32 -> 32 drum midi 43 112 -> 102 drum midi 45 0 -> 10

Exactly ten notes moved from Very Low Tom to Low Tom, five in each bar. Nothing was added, removed or reordered.

Beats are shared definitions in GPIF. Bars 5 and 16 share their Beat elements for the plain notes and carry their own for the ghosts, so repointing bar 5 fixed four of bar 16's five slots at once. The first run named both bars, hit the mismatch on the second, and refused with exit 2 having written no file. The tool now validates every named bar before it mutates anything.

The gate itself

The single-song rule is doing real work and it is worth keeping. Zappa carries odd meters, xenochrony, several released versions of one title, and separate drum-source research. A chat that carries two songs runs both of them thin. That reasoning holds up under this audit.

The rule has three defects, all visible in this run.

DefectWhat it causedEvidence
Keyed on title, not id Two different Zomby Woof tabs edited as if one song s412162 + s5820647
No time ceiling One chat ran 113 hours against the end-and-clear rule 01 Sep 04:59 to 05 Sep 22:09
Third branch has no floor Blocked song plus never-stop equals unbounded output 3,208 assistant turns

The fix

#ChangeWhere it lives
1 Lock on the Songsterr song id, and read the title back from api/meta/<songId> ahead of any edit. The first amendment already carries this and it needs enforcing. feedback_zappa_one_song_per_chat_hard_gate.md
2 Give branch three a completion definition. Name the evidence tasks at the start, work the list, then the song is finished even while the upload path is walled. same file, second amendment
3 Add a turn ceiling to the gate. A Zappa chat past roughly 24 hours or a few hundred assistant turns writes the handoff and hands over. feedback_end_long_sessions_clear_hard_gate.md
4 Ban peer steers that propose destructive acts. A babysitter session reports and relays. It never proposes deletion on a shared artifact. new memory, peer steer safety
5 Put the real ask first in a new chat so the auto-title stops colliding, or rename by hand at the start. habit, no file needed
