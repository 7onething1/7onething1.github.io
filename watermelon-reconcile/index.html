The provenance test

The question is whether the doubled note belongs to the original transcriber or arrived in our own later editing. Revision r7715683 answers it directly. What that ceiling actually means

The promotion gate is built to bless edits that rest on stem timing, and it requires a CONFIRMED alignment before any stem evidence may support an edit. This alignment is not CONFIRMED, so that gate would refuse, and it should.

The 63 removals do not rest on stem timing. They rest on provenance: the author's own revision r7715683 writes exactly one plain stroke at all 63 positions, unanimously, which is a document fact that needs no clock. The stem result above is corroboration for two thirds of them and it is not the basis. Nothing here is promoted as stem-validated.

Four ways to read this file and get a clean wrong number

Between two sessions, every one of these ran without erroring and returned a confident figure.

MistakeWhat it returnsWhy it looks fine
Counting note ELEMENTS as notes445 against an expected 191GPIF deduplicates; elements are definitions, not events
Joining on a reader that exposes no note id"2834 disagree"every row compares against None and None never matches
Looking for <Property name="InstrumentArticulation">0 disagreementsit is a DIRECT CHILD of <Note>. The Properties list holds only ConcertPitch, Fret, String, TransposedPitch, Midi and the bend fields, so the search finds nothing on every note and reports a silent zero
Applying one track's kit table to every track~416 disagreements in every filenote elements are shared across tracks, so a drum kit table gets applied to guitar pitches

Verified here: searching the Properties list for InstrumentArticulation finds it on 0 of 15 reachable notes, which is exactly the silent zero.

The rule: a dual-field checker must test for DISAGREEMENT between the fields, never for a sentinel value. The missing-value case and the disagreeing-value case do not overlap in these files, so a sentinel test cannot see this defect at all.

A checker keyed on Midi == -1 would pass this file. tr_ledger.py:189 warns that reading only the Property returns −1 for every drum note. Measured here, 0 of 15 notes read −1 in v13 and 0 of 14 in the chart build; their Midi properties carry real values that agree with the articulation everywhere except those two definitions. The missing-value case and the disagreeing-value case are separate failure modes.

The source layer, checked rather than assumed

  • A higher-resolution master would not help. The stem source here is 44.1 kHz 16-bit with 2.56% of its energy above 20 kHz, so it is full-bandwidth and not lossy-derived. Drums live well below that ceiling, so 96 or 192 kHz adds nothing to separation.
  • Commercially sold "stems" for this album are re-recorded by session musicians rather than the original multitrack, so they answer which tom a session player chose, never which one Colaiuta struck.
  • The one artifact that would settle it is the original studio multitrack, with each tom on its own mic. It is not publicly released.

So per-head identity is not pending work. It is closed at a named layer, and the tab's tom lane assignments stay as the chart and the transcriber wrote them.
