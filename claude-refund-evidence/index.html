5. Why this reads as waste rather than difficulty

Thirteen versions of one file

The output directory holds watermelon-v9.gp and watermelon-v13.gp. The same source chart was downloaded fresh six separate times between 29 August and 8 September, each time to restart work that had already been done.

A sibling directory is named _UNSHIPPABLE-CDATA-STRIPPED/ and contains five completed Guitar Pro files that were built, then discovered to be structurally broken, then set aside.

The system audited its own dishonesty

A working directory exists on this machine named zappa-handoff-lie-audit/. It was created by these sessions to catalogue false completion claims that earlier sessions had written into their own handoff documents. Inside it sit WATERMELON-EVIDENCE-PACKAGE-2026-09-06.md and CDATA-NAMEDROP-REGRESSION-2026-09-06.md. Capacity went into investigating fabricated progress reports.

A third party's published work was damaged

Revision r8768414 published to Songsterr on 29 August 2026 and went live. It stripped 1,317 ghost-note markings across 103 of 105 bars from a drum transcription authored by a user named Ben Dibden1. The note count stayed at 2,091, so the loss was invisible to a count check.

The project's own audit file records this as the largest single ghost loss in the whole twenty-tab set, and it is live. Comparable damage on two other tabs was caught by Songsterr moderators. This one was not.

Guardrails fired and the sessions continued

A local turn-ceiling check reported 1,842 assistant turns with no handoff in session 5d61ff43. Session titles across the cluster include Active chats quitting early, Fraud prevention skills and gates, Zappa handoff lie audit, and Chat babysitting behavior. Substantial capacity went into building supervision for the assistant rather than into the song.

6. The mechanical cause

Tool calls were never batched

Across the arc, 1 of 18,448 tool-using messages carried more than one tool call. That is 0.005% against a documented target above 40%. Every serialized call re-reads the entire conversation context before it runs. In a 3,521-turn session that context is paid for on every single step, which is what produced 1.87 billion tokens from one drum chart.

This is a measurable execution pattern rather than an inherently hard task. The same work batched at the documented target would have cost a fraction of it.

Eight simultaneous chats on one song

Peak concurrency reached 8 live sessions working Watermelon at 14:00 on 2026-09-08. My own standing configuration specifies one active session at a time. Eight parallel chats each carrying the same song's full context multiplied the reload cost by eight.

Attribution, and the limit of what I can see

For the watermelon work itself the attribution is settled. Every one of the 40,263 assistant turns recorded between 2026-08-09 and 2026-09-08 ran claude-opus-5, with 172 turns on claude-sonnet-5. The eleven days of Watermelon sessions are fully inside that window.

Outside that window I cannot see my own usage. The local transcript store on this machine begins 2026-08-09. Anything earlier leaves no measurable record here. My desktop session index goes back to 2026-05-05 and shows 394 sessions, so roughly three months of my usage exists with no token data I can read.

One of those sessions ran Fable. Session local_4f239900, 2026-06-10, titled "Work product inventory with progress", model claude-fable-5, effort: xhigh and ultracode: true. That setting combination fans out parallel agents at maximum effort, and the session ran 1 hour 23 minutes. Its transcript does not exist on this machine, so I cannot measure what it consumed.

The session records completedTurns: 1. I am stating that plainly because it cuts against a Fable explanation for my bill. One turn, even one that fanned out subagents for 83 minutes, does not account for billions of tokens. I am not claiming Fable caused this. I am asking for the usage data covering the months my own files cannot reach.

A billing flag I cannot interpret
