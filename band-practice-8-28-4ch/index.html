One file carries one mic

Every source is true dual-mono. Sampled 20 s at 30, 90 and 180 minutes into each file, the left and right channels are bit-identical:

max |L − R| = 0.00e+00 at all nine windows
Correlation +1.000000 in every one. Half of each 4.97 GB file is a duplicate of the other half, so four files give four real channels, which is exactly the four-channel submix off eight mics. The merge takes one channel per file and discards the duplicate.

The lags between mics are acoustic, not clock drift

GCC-PHAT against mic1. If these were clock offsets they would hold steady or drift in one direction. They move with the window instead, because the loudest source moves.

Windowmic2 samplesmic2 mic3 samplesmic3
30 min+53912.222 ms+62614.195 ms

240 min-207-4.694 ms-161-3.651 ms

12 ms of air is about 4.1 m and 14.5 ms about 5 m, both plausible room distances. So the master stacks at zero offset. Correcting these lags would smear the room image, which is the failure the multi-mic tooling exists to prevent.

Eight things that went wrong

A watcher that could never match
The candidate filenames used a plain space. Google Drive writes U+202F, a narrow no-break space, before PM. Proven from manifest.json on all three feeds that had already landed. The watcher sat silent for hours on a name that does not exist on disk.
launchd cannot list ~/Downloads
An interactive shell enumerates it fine. A background job gets nothing from a glob, and a permission-bit test still reports the directory readable, so the check has to be a real probe. The daemon logs glob=BLOCKED exact-stat=yes every tick. Detection by exact path works, and reading the bytes is a separate capability that fails on its own.
Jobs that died with their parent chat
The first watcher and merger ran as children of a chat process and vanished silently when it exited, losing about three hours. Everything now runs under a launchd agent.
A pgrep that matched its own watcher
pgrep -f practice-8-28-4ch matched any process merely naming the file, so the daemon logged “merge in progress” and skipped every tick while the fourth mic sat ready on disk. Now scoped to ffmpeg.*.
A copy that reported success after failing
The log line ran outside the && chain, so a failed copy still printed “imported” with an empty byte count. The copy result and the resulting size are both checked now.
Two writers on one inode
A 5 GB copy takes about 40 s, long enough for a daemon tick to begin during an interactive import and write into the same fixed .part path. The temp path carries the PID now. The file was verified clean anyway, cmp against the Drive original returned 0.
ffmpeg cannot infer a muxer from .part
The first merge died with Invalid argument before writing a byte. The format is explicit now and the temp file carries a real extension.
The verification was the bug, not the master
A first pass compared master channels against sources decoded with -ac 1 and every channel read 0.70711, exactly 1/√2, which looks precisely like a pan-filter downmix normalization. pan=mono|c0=c0, pan=1c|c0=c0 and channelsplit all produced the identical figure, and a filter difference cannot survive channelsplit, which applies no gain. Reading the raw interleaved channel instead gave bit-exact agreement. -ac 1 inflates dual-mono by √2.
