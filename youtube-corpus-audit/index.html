Why the retrieval index could not answer any of this

CONFIRMED

Ollama.app was in the Trash, so /ask could not embed

The live ollama server, pid 1991, up 3 days 22 hours, executes from /Users/drwu/.Trash/Ollama.app/Contents/Resources/ollama. The app was moved to the Trash and the running server was never restarted. The process survives because its binary stays open, so /api/tags answers in milliseconds and lists all six models including nomic-embed-text. It can no longer spawn a model runner, so every embed call hangs: /api/embeddings and /api/embed both returned http 000 after 25 and 30 seconds. One 53 MB ollama process sits there with no runner beside it, and 91% of memory is free, ruling out memory pressure. The ollama CLI is also gone from PATH.

What it means. /ask has been running with its corpus, vault and memory layers dead, falling back to a coarse scan of chat transcripts. Its “0 relevant cited results” means not searched, never nothing there. This whole audit was done by reading the filesystem and the handoff docs directly, because the index could not be consulted.

RESOLVED

Retrieval is live again, on Brandon's go-ahead

Neither the Trash copy nor /Applications/Ollama.app existed by the time the repair ran, so there was nothing to put back. Homebrew carried the formula and began building openssl@4 from source, since Ventura on x86_64 no longer receives bottles, which placed a long compile chain ahead of ollama itself. The route that worked was the vendor's own prebuilt server tarball, ollama-darwin.tgz v0.40.11, 181,324,349 bytes, sha256 aea7d3f2e32371b7644a6e2ec8d4f26820a0e3965918cce8a46cef3e947f6291. It is a flat tree of the ollama binary beside its libggml and libllama runners, so the tree has to stay together for the runner to load. It installed to ~/.local/opt/ollama-0.40.11 with a symlink at /usr/local/bin/ollama, which also returns the ollama CLI to PATH. The old root-owned dangling symlink was kept beside it as ollama.dangling-symlink-kept-2026-10-26 rather than discarded.

Proof. The 0.24.0 server on the unlinked inode was stopped and pid 18600 now reports 0.40.11, with all six models intact across the version jump. /api/embeddings and /api/embed each return 768 dimensions, and ask.embed() returns 768. corpus_test.py reports 10 of 10 domains COVER, 100 / 100. /ask on the music question returns 20 cited results in 35.7 seconds with the vault, memory and corpus-registry layers all scoring above the 0.60 gate, against 0 results before the repair. The layer indexes were intact throughout: vault 24,604 rows, domain 2,781, memory 331, corpus 20.

It survives a reboot. ensure_ollama.py ends in a branch that runs ollama serve when the server is down, resolved off PATH, so that branch was dead for as long as the CLI was missing from PATH. Restoring the symlink reconnects it. Tested by killing the server and running the hook the way SessionStart does: it printed “started ollama serve”, pid 22825 came up on 0.40.11, an embed returned 768 dimensions, and a second run reported healthy. The test is self-authored, and it ran the real hook against a really downed server, so the next session recovers without help.

FIXED

The hook that called that server healthy

ensure_ollama.py probed /api/tags with a 1 second timeout and printed “/ask embed server already up” at every session start. That is a liveness check that cannot fail the way the tool fails, so it green-lit a dead embed path. It now requests a real embedding with an 8 second budget and prints a DEGRADED warning naming the cause and the fix.

Proof, and it has now fired for real. The app was quit and this session resumed, and the hook printed the full DEGRADED warning unprompted at SessionStart, naming the lost model runner and the fix. That is an unplanned production firing rather than a fixture written for it, so the earlier “not proven in production” caveat is retired. Backup kept at ensure_ollama.py.bak-before-embed-probe-2026-10-26. The healthy-case cost is measured now as well: with the server repaired it prints “/ask embed server up and embedding.” in 0.36 s cold and 0.19 s warm, exit 0. One caveat for anyone testing it by hand, line 57 drains stdin to close the harness pipe, so run it as python3 ensure_ollama.py < /dev/null or it blocks on stdin and looks like an ollama hang.

Row floor on both index builders

normalize_indexes.py and build_lesson_index.py now route every index write through one shared write_with_row_floor(). It reads the key count already on disk, refuses to replace the file when the new pass produces fewer keys, saves the rejected output as <name>.json.rejected, keeps a .bak-<date> of the file it does replace, and exits 2. A --allow-shrink flag is the only override.

Proof.
